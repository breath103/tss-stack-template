# Running e2e from agents/scripts — gotchas

- **Restart Chrome before EVERY run: `./scripts/e2e.ts stop && ./scripts/e2e.ts start`.** Unconditional. Not "if it hangs", not "if it looks wedged" — every time, before the scenario. A stuck headless Chrome (crashed tab, orphaned CDP session, a modal dialog that blocked all further events) is the single most common cause of a hung run, and it is *indistinguishable from a slow run* until you have already burned minutes staring at a frozen log. A clean start costs ~1s; a wedged instance costs you the turn. Reusing a warm Chrome to save that second is never worth it.
- **Still hanging after a clean Chrome? THEN debug the scenario.** This is a *local* browser against a *local* server; nothing here legitimately takes more than 2–3 seconds, so a run that hasn't finished in a few seconds is wedged, not slow. Do NOT re-read a frozen run, add `console.log`, or bump timeouts.
- **Timeouts live in the scenario, not the shell.** `harness()` accepts `{ timeoutMs }` — set it in the test file. Don't wrap calls in `timeout N` from the outside. The runner force-exits at the end so dangling supabase/websocket/MQTT clients can't keep the process alive past the summary.
- **Never `2>&1 | tail -N` a backgrounded run.** `tail` buffers everything until EOF, so the log file stays empty for the whole run and looks identical to "stuck." Either run foreground (output streams directly) or redirect raw (`> log.txt 2>&1`) and `tail -F` the file.
- **Dev server too.** `./scripts/dev.ts status` first — if it's not `ready`, start it and wait; don't blindly invoke e2e. (Unlike Chrome, do NOT restart a healthy dev server — the backend's readiness gate may not re-pass and you'll strand ports.)
- **A `page.goto` that times out at the harness nav cap is usually the env, not your code — and not a wedged server.** The runner sets `setDefaultNavigationTimeout(1000)`; a cold Vite dev `load` (unbundled module graph) can exceed that locally. Before you touch anything, run an *untouched* scenario — if it times out on `goto` identically, it's the harness cap, so verify your change via a standalone Playwright pass with a normal timeout. Restarting the dev server won't help — see the previous bullet.
- **Never run a scenario while another run is in flight.** Every scenario reseeds, and they all share one DB, one dev server, and one Chrome — a foreground run against a backgrounded suite silently corrupts both sides' data, so failures and passes are equally meaningless. One run at a time; if you backgrounded a suite, wait for it or kill it first (killing mid-run also leaves `e2e/fixtures/<scenario>/` wiped, since each scenario clears its dir on start — `git checkout -- e2e/fixtures/` to restore).
